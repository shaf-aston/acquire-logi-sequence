PBS-01 · Product breakdown structure

3D stacking & multi-van load allocation

The algorithm that decides where every box goes — which corner, which way up, which level, which van, and in what drop order — broken into parts you can build and tick off one at a time.

4 levels6 product areasOrdered by dependencyDecomposes the van-loading engine

What got collapsed first

The load engine looks like a dozen features. It is really three engines wearing different clothes. Naming that before the tree is the point of the exercise — it stops the same physics being written five times.

  • Van packing, pallet building, and shared-truck stacking are one packer. Boxes-in-a-van, items-on-a-pallet, and pallets-in-a-truck are the same problem with a different container. One packer, three container adapters.
  • Drop-order zoning, re-optimise, and the bulk fast path are not packers. They are wrappers that slice, re-feed or multiply the same packer. The packer never learns what a stop or a rearrange is.
  • Fragile, brittle, crush limit, weight ceiling and reach height are one gate. Not five rules in five places — one legality function that the auto-packer, the drag editor and the re-optimiser all call. Change physics once, it changes everywhere.

The ordering below is dependency order: nothing in an area can exist until the area above it does. That makes it double as a build sequence. The last area sits outside the sequence because it is underneath all of it.

1.0Cargo physics model

What a box is and what it can bear. Everything downstream is arithmetic on these numbers, so a wrong number here is a wrong load plan no amount of clever packing can fix.

1.1Item construction

1.1.1Dimension resolution

  • Column-to-axis mapping — the sheet's Length / Width / Height become the van's front-back, side-side, up
  • Quantity expansion — one row saying "qty 3" becomes three separate boxes to place
  • Missing-dimension refusal — a blank size sets the item aside with a written reason, never a made-up numbernever guess
  • Third-dimension derivation — two sizes plus a real weight can calculate the third; the one permitted exception

1.1.2Weight resolution

  • Stated weight pass-through
  • Density estimate — volume × the category's typical weight-per-cubic-metre when the sheet gives none
  • Per-pallet weight from a cargo summary — unit weight × quantity ÷ pallet count, with a sanity check on the result

1.2Bearing strength — "what may sit on top of this"

1.2.1Category limits

  • Crush limit in kPa — how much squeeze per square metre the top face survives
  • Weight ceiling in kg — a hard cap on total kilos above; zero means nothing may ever sit on it
  • Category density table — feeds the weight estimate above

1.2.2Material tightening

  • Strength tier → kPa map — none / low / medium / high, set in config not code
  • Tighten-never-loosen rule — a machine guess may only lower a limit; a human override replaces itinvariant
  • Squashy discount — foam and fabric take a further cut because they compress
  • Brittle discount + low-tier cap — stone and glass are capped low first, then discounted, so an unconfident guess can't out-rank a correct one
  • Rotation lock — fixed / upright-only / free; which ways up this item may legally be turned

1.2.3Classifier swap-seam

  • Keyword rule engine — the default, works offline, no API key
  • LLM engine behind the same interface — same labels out, so nothing downstream knows which ran
  • Fallback chain with a dead-key path — a 401 from the provider degrades to rules instead of failing the quote

1.3Bulk reduction — shrink a giant order before packing

1.3.1Grouping strategies

  • Identical-SKU blocking — fourteen thousand matching boxes get taped into a few big ones
  • Mixed-SKU pallet layering — different small boxes stand side by side, one layer high, on a standard pallet
  • Delicate isolation — fragile goods get their own pallet with nothing above them
  • Stated pallet totals — a sheet saying "14 pallets" is quoted as 14 pallets, not 14,000 loose pieces

1.3.2Grouping guarantees

  • Piece-count conservation check — grouping only regroups; a lost or invented box is a test failure
  • Weakest-member strength — a bundle is only ever as strong as the flimsiest box in it
  • Threshold config — the order size at which grouping switches on lives in JSON; small orders skip it entirely

Everything above produces numbers. Area 2 is the only place those numbers become a yes or no. It is deliberately the smallest area in the tree and the one with the most tests — because three separate front-ends depend on it agreeing with itself.

2.0The placement gate

One function answering one question: may this box sit exactly here? The auto-packer, the operator's mouse, and the re-optimiser all ask it. None of them are allowed their own opinion.

2.1Geometric legality

2.1.1Fit and collision

  • Interior bounds test with clearance slack — does any part poke through a wall or the roof
  • Overlap test with a hair of tolerance — boxes touching is legal; a fraction-of-a-millimetre float wobble must not read as a clashbug-prone
  • Orientation enumeration — all six ways up, filtered by the item's rotation lock

2.1.2Spatial index

  • Uniform grid over box footprints — so "what's near here?" checks a handful of boxes, not all of them
  • Superset contract — the grid may return extras; the caller re-runs the exact test, so extras cost time not correctness
  • Insertion-order preservation — results come back in the order boxes were placed, so adding up weights gives the identical answer every runinvariant

2.2Support legality — the stack maths

2.2.1Held-up checks

  • Full-footprint coverage across several bases — a shelf may span two cabinets, but no corner may float
  • Fragile-base veto — a standard box may never rest on something marked fragile
  • Crush check by pressure — weight ÷ contact area, so a small heavy box can't punch through a wide light one
  • Weight-ceiling accumulation — running total of everything already resting on that base, plus the newcomer's share

2.2.2Column push-down

  • Recursive load transfer to the floor — new weight is charged to every box in the column below, not just the one directly under
  • Per-level re-check — five boxes each fine in a pair are still refused if the bottom one ends up carrying all four
  • Rounding-tolerance band — stops a load exactly at the limit flip-flopping between accept and rejectbug-prone

2.3Human-reach legality

2.3.1Reach cap

  • Base-height ceiling — how high a worker can set a box down by hand; one fleet-wide number in config
  • Per-job override — a checkbox turns it off for this pack only, and the 3D editor honours the same setting
  • Rotation rescue — a box laid flat may clear the cap where standing up couldn't, so every allowed turn is tried against it

2.3.2Reason attribution

  • Reach-blocked vs genuinely-full split — re-runs the search with the cap lifted, only when something failed, to say which it was
  • Most-specific-failure-wins ordering — "crushes the cabinet below" beats a generic "won't fit"

2.4Verdict reporting

2.4.1Per-box load report

  • Load-on-top figure per placed box — feeds the meter in the table and the colour in 3D
  • Overload flag reconciliation — the warning badge is the gate's own verdict, so the picture can never disagree with the physics
  • Whole-arrangement re-validation — one call that re-checks an entire van after any edit

Only now does a packer make sense. Note what area 3 does not contain: any judgement about safety. It scores spots the gate already approved — that separation is why a hand-dragged box and an auto-placed box obey identical rules.

3.0Single-container packer

Fill one container, one box at a time, never moving a box once it's down. Fast and always safe; it leaves a little space on the table on purpose.

3.1Load ordering

3.1.1The sort that decides the layout

  • Sturdy-first grouping — anything fragile or brittle sinks to the back of the queue so it lands on top
  • Crush-limit descending — the strongest of the eligible group goes down first and becomes the platform
  • Volume descending — big sturdy boxes make a wide, flat floor for everything else
  • Stable id tie-break — identical items always resolve the same way, so two runs match exactly

3.2Corner search — the "many sides" mechanism

3.2.1Anchor generation

  • Origin seed — an empty van offers exactly one corner: the front-left floor
  • Three-sided spawn per placed box — every box that lands opens a corner to its right, one beside it, and one on its top
  • Anchor cap with lowest-and-most-compact retention — keeps the list short on huge orders without losing the good spots
  • Corner-only limitation, documented — corners appear at box edges only, never projected onto walls or faces; this is the known gap

3.2.2Cheap rejects before the expensive scan

  • Payload short-circuit — would this box tip the van over its legal weight
  • Any-rotation fit test — is it simply too big for this container in every allowed turn
  • Remaining-volume test — is there less free space left than the box occupies

3.3Spot scoring — the "many levels" mechanism

3.3.1Score terms

  • Build-upward reward — the dominant term; the packer is always trying to gain height
  • Sit-on-something reward — resting on an existing box beats opening a fresh patch of floor
  • Near-origin nudge — a tiny pull toward the corner so no stranded gaps are left behind
  • Lie-flat nudge — a tiny preference for the lowest profile, leaving headroom for another layer
  • Weighting ratio in config — the two "up" rewards outweigh the nudges by a thousand to one; that ratio is the tuning knob

3.4Throughput guards

3.4.1Hot-loop protection

  • Full-container short-circuit — once nothing more fits, the next box is rejected instantly
  • No-room memo per box type — "boxes of this exact shape had no room" is remembered, so thousands of identical ones finish fast
  • Per-pack box cap — an upper bound on boxes in one pass, so a job always returns in a predictable time

3.5Container adapters — one packer, three containers

3.5.1Adapters

  • Van interior adapter — the default: boxes into a vehicle's load space
  • Single-pallet adapter — loose items onto one pallet, with a height cap so the result still fits a van
  • Shared-truck adapter — whole pallets treated as the boxes, the truck as the container
  • Owner tagging through the adapter — each placement carries which company owns it, for per-company colour in the viewer

Area 4 is where "multiple vans" actually lives — and it answers a different question from area 3. Inside a van, ordering is decided by strength. Between vans, it is decided by cost. Nobody hand-steers heavy cargo into van one.

4.0Multi-container allocation

Which vehicles, how many, and — when there are several drops — what goes nearest the doors. Every wrapper here calls the area-3 packer unchanged.

4.1Single-vehicle ranking

4.1.1Rank rules

  • Assemble-once, pack-into-each — items are built one time and reused across every candidate vehicle
  • Fits-everything first, then tightest fill, then most-placed — the ranking order, in that priority
  • Honest single-van flag — tells the quote plainly whether one vehicle really covers the job

4.2Cheapest fleet set

4.2.1The search

  • Branch-and-bound over vehicle combinations — minimises total per-mile cost, since the trip distance is the same whichever vans you pick
  • Step-bounded greedy fallback — past a set number of search steps it switches to a simpler split, so the loading dock never waits
  • Payload-aware cost rate — a heavily loaded van costs more per mile than an empty one
  • Deterministic tie-break — two near-identical fleet options always resolve the same way

4.2.2Fleet source

  • File-backed fleet with an in-memory override — the swap-seam that lets a session add a vehicle without editing config
  • Size-class inference for a session-added van — works out where a new vehicle sits against the existing fleet

4.3Drop-order zoning

4.3.1Banding

  • Dynamic depth bands, door-first — the first delivery sits at the doors, later ones deeper toward the cab; no digging
  • Band-boundary clearance sliver — a hair of space keeps zones physically distinct and guards against float drift
  • Untagged-cargo final band — items with no drop tag go deepest rather than being dropped for lacking a tag
  • Payload threaded across bands — weight is a whole-van limit, so each band gets what's left, not a fresh allowance
  • Contiguous continuation across vehicles — a stop cut off at van one's cab resumes at van two's doors

4.3.2Drop attribution

  • Strict Stop-column parse — only a bare whole number counts; headings and sub-totals are skipped, not guessed at
  • No-column neutrality — a single-drop sheet is completely unaffected
  • Per-row drop tags surfaced in the UI — the operator sees and can correct the attribution

4.4Bulk fast path

4.4.1Pack-one-multiply

  • Representative-van real pack — one vehicle packed with genuine geometry, then multiplied arithmetically
  • Remainder packed for real — the partial last van goes through the normal allocator
  • Identical-result guarantee — for a single-product order the fleet must match what the slow path produces, pinned by testinvariant
  • Eligibility test — a mixed order falls back to the normal path rather than approximating
5.0Operator control surface

Where a person overrides the algorithm — and the machinery that stops an override from producing an illegal van. The 3D viewer itself already exists and is untouched; these are the algorithm-side pieces it calls.

5.1Re-optimise

5.1.1Scope

  • Per-vehicle re-pack — re-runs the real packer over exactly what is in this van now, keeping the operator's van-to-van decisions
  • Whole-fleet re-pack — same, across every vehicle at once
  • Real payload enforcement — over-weight units come back as unplaced with the packer's own reason, never quietly loaded
  • Drop-order preservation — a multi-drop van re-packs through the zoned wrapper, so re-optimising cannot destroy the delivery bandingbug-prone
  • No-gain no-op — re-optimising twice returns the same layout

5.2Manual edit, same gate

5.2.1Edit actions

  • Drag with snap-onto-support — a dragged box settles onto whatever holds it, and commits only if the whole van still passes
  • Move between vehicles — finds a safe spot in the target, then re-validates that entire vehicle
  • Unplace to a persistent tray — the tray lives above the per-van view, so nothing is lost when switching vehicles
  • Flattest-orientation default on drop — a box that only failed standing up arrives pre-turned, instead of repeating the same failure
  • Reset to computed plan

5.3Truth surfaces — showing what the algorithm couldn't do

5.3.1Never-guess displays

  • Unplaced list with written reasons — visible text, not a hover tip, at result level rather than buried in the 3D canvas
  • Unit-accurate counts — tiles count real items, not the bundles they were grouped into
  • Load-on-top meter per box — how close each item is to its crush limit, in the table and as colour in 3D
  • Reach-blocked banner — counts items refused only by the height cap and points at the toggle that lifts it
  • Per-stop colouring — which band belongs to which drop, at a glance

The last area is not a stage. It sits underneath every branch above and is the reason the others can be trusted.

6.0Cross-cutting foundations

Config, determinism, diagnostics and the honest list of gaps. Underneath all five areas, sequenced with none of them.

6.1Configuration surface

6.1.1Tunable knobs, none in code

  • Fleet and per-mile rates
  • Category strength matrix and densities
  • Strength tier → pressure map
  • Grouping thresholds and pallet spec
  • Clearance, reach cap and search bounds — tolerances and limits as named values, not numbers scattered through the packer
  • Single environment reader — one module reads environment settings; nothing else does

6.2Determinism guarantees

6.2.1Same input, same plan

  • No clocks, no randomness anywhere in the packing path
  • Stable sorts throughout — equal items never swap places between runs
  • Fixed-order weight summation — adding the same numbers in a different order gives a different last decimal, which can flip an accept into a rejectinvariant
  • Golden-master test — an optimisation that changes even one placement fails the build

6.3Diagnostics

6.3.1Why isn't this van fuller?

  • Missed-opportunity vs physical-limit verdict — the one signal that says whether low fill is a bug to fix or physics working correctly
  • One verdict, shown in two places — the behind-the-scenes trace and the on-screen panel use the same answer, so they cannot disagree
  • Command-line pack trace — replay a job's packing decisions outside the app
  • Per-van fill panel — the same verdict shown beside the 3D model

6.4Known gaps, held open deliberately

6.4.1Buildable improvements

  • Wall-and-face corner projection — today corners only appear at box edges, so some valid pockets never get tried
  • Settle pass — a cheap final nudge of boxes toward the floor to reclaim gaps that opened later
  • Retry pass for unplaced items — one second attempt for anything an earlier box crowded out

6.4.2Out of scope, stated as such

  • Braking, cornering and vibration forces — only up-and-down loads are modelled today
  • Centre of gravity and axle-weight balance
  • Step-by-step load sequence for the loader — the plan says where, not the order to carry them in

The four edges that actually matter

Area 3 has no opinion about safety — and that's the whole architecture. The packer only scores spots that area 2 already approved. So any physics change is a single edit in the gate, and it propagates to auto-packing, mouse-dragging and re-optimising for free. The moment a packer starts making its own legality call, the three surfaces begin to disagree and every bug becomes a hunt for which one is right.
Load-order rules are wrappers, not packer features. Drop-order zoning slices the container and hands each slice to the untouched packer. That means the next load-order rule you want — weight forward, axle balance, heaviest-last — is a new wrapper, not a packer rewrite. Cheap now; very expensive if the first one is written into the packer instead.
Determinism is retroactively impossible. Fixed-order summation is why the same van always gives the same verdict at the exact crush limit. Introduce parallel packing, or a lookup whose order isn't fixed, anywhere in areas 2–4, and the results shift silently — no crash, just a plan that quietly differs from yesterday's. Retro-fitting this after the fact means re-deriving every stored plan. Build it in from day one, or never.
The unplaced list is the product, not an error state. Every branch feeds it: refused sizes from 1.1, crush refusals from 2.2, reach refusals from 2.3, overflow from 4.2. It is the one surface where the system admits what it couldn't do, and it is the difference between a quote an operator trusts and one they re-check by hand. Under-build it and the rest of the engine's honesty is invisible.
